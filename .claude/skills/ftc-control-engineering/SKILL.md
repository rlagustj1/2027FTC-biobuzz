## 왜 이 스킬이 필요한가

웹 코딩에서는 화면을 보고 바로 잘못을 판단할 수 있고, 실패해도 새로고침하면 그만이다. FTC 제어 코드는 다르다: 실제로 로봇을 굴려봐야 맞는지 알 수 있고, 잘못된 파라미터는 모터를 태우거나 로봇을 충돌시킬 수 있다. 그래서 "AI가 그럴듯한 숫자를 채워 넣고 넘어가는" 기본 습관이 여기서는 위험하다. 이 스킬은 그 습관을 억제하고, 대신 실측·시뮬레이션·단계별 검증을 강제하는 워크플로로 유도한다.

## 1. 튜닝 파라미터는 절대 확정값으로 채우지 않는다

다음 값들은 실측 전까지 "이론적 추정치/플레이스홀더"임을 코드에 명시한다:

- `VMAX`, `AMAX`, `JMAX` (모션 프로파일)
- `kP`, `kI`, `kD`, `kF` (PIDF 게인)
- 모터 free speed, 기어비, 바퀴 반지름 등 하드웨어 스펙

형식:

```java
// TODO: 실측 필요 — goBILDA 5202 free speed 기준 이론값이므로
// 실제 로봇에 올려서 배터리 전압/부하 상태에서 재측정할 것
double VMAX = 2800; // 틱/초 (임시값, free speed의 약 80%로 추정)
```

"일반적으로 이 정도 씁니다"라는 값은 참고용일 뿐, 사용자가 실기에서 재측정하기 전까지 최종값으로 취급하지 않는다.

## 2. 단위를 항상 명시하고 검증한다

가장 흔한 버그는 단위 불일치다. 함수를 쓰거나 고칠 때마다 확인:

- 시간: 초(s) vs 밀리초(ms)
- 각도: 도(degree) vs 라디안(radian)
- 거리: 인치(inch) vs cm vs 엔코더 틱(tick)

모든 함수 시그니처에 단위를 주석으로 명시:

```java
/**
 * @param targetPosition 목표 위치 (엔코더 틱 단위)
 * @param currentVelocity 현재 속도 (틱/초 단위)
 * @return 모터 출력 (-1.0 ~ 1.0)
 */
```

## 3. 작은 단위로 쪼개서 순차 검증한다

한 번에 전체 시스템을 완성하려 하지 않는다. 사용자가 통합 코드를 한 번에 요청해도, 아래 순서로 쪼개서 진행할 것을 제안하고 **사용자 동의 없이 4단계 이상을 한 번에 진행하지 않는다**:

1. 프로파일 생성 함수만 작성 → Python 시뮬레이션으로 v-t, x-t 그래프 확인 → 사용자가 모양 확인
2. PIDF 컨트롤러만 별도 작성 및 단위 테스트
3. 프로파일 + PIDF 통합 (시뮬레이션 환경)
4. Java(FTC SDK)로 이식 — 이 단계부터 실제 로봇 필요
5. 실제 로봇에서 파라미터 튜닝 — AI가 대신할 수 없음, 사용자가 직접 실기 테스트

## 4. 시뮬레이션 우선, 실기는 나중

로직 검증은 Python(numpy/matplotlib)으로 먼저 한다:

- 사다리꼴/S-curve 프로파일의 위치·속도·가속도 그래프를 그려 이론적으로 맞는 모양인지 확인
- 목표 거리와 프로파일 아래 면적(적분값)이 일치하는지 수치적으로 검증하는 assert 포함

시뮬레이션에서 검증되지 않은 로직은 Java(FTC SDK)로 이식하지 않는다.

## 5. 짧은 거리(삼각형 프로파일) 분기 처리 필수

목표 거리가 짧아 vmax 도달 전에 감속을 시작해야 하는 경우를 반드시 분기 처리한다. 빠뜨리면 짧은 이동 명령에서 프로파일이 깨진다:

```
if (가속+감속에 필요한 최소 거리 > 목표 거리):
    → 삼각형 프로파일로 전환 (실제 최고속도는 vmax보다 낮음)
else:
    → 표준 사다리꼴 프로파일
```

## 6. 원리를 항상 설명한다

코드를 제시할 때마다 "왜 이렇게 짰는지"를 함께 설명한다. 특히:

- PIDF에서 F(피드포워드)항이 왜 그 위치(가산 순서)에 들어가는지
- 프로파일 재계산 주기가 왜 그 값인지(제어 루프 주기와의 관계)

이는 세특 탐구 산출물로서 사용자가 원리를 이해하고 있음을 보이기 위한 필수 과정이다. 코드를 실행만 하고 원리를 모르는 상태로 넘어가지 않는다.

## 7. 실측 후 이론-실측 비교 그래프를 남긴다

실기 테스트 후에는 엔코더 로그를 저장하고, 이론 프로파일(목표 v-t)과 실측 프로파일(실제 v-t)을 겹쳐 그린 비교 그래프를 생성한다. 오차 원인을 다음 중에서 분석한다:

- 모터 토크/속도 한계(saturation)
- 배터리 전압 강하
- 바퀴 슬립
- 제어 루프 지연

## 8. 파일은 정해진 패키지 구조를 따른다

새 FTC(Java) 파일은 아래 구조에 맞춰 배치한다. `teamcode/` 루트에 흩뿌리지 않는다.

```
TeamCode/src/main/java/org/firstinspires/ftc/teamcode/
├── opmodes/            OpMode만 모음 (@TeleOp/@Autonomous)
│   ├── TeleOp/           수동 조종 OpMode
│   ├── auto/             자율주행 OpMode
│   └── tests/            하드웨어/기능 테스트용 OpMode
├── subsystems/         드라이브트레인·팔 등 하드웨어 서브시스템 (FTCLib SubsystemBase)
├── commands/           동작 단위 Command (FTCLib CommandBase)
├── localization/       오도메트리·야코비안 등 위치추정/기구학
├── comm/               외부 PC 통신 (소켓 서버 등)
└── Utils/              공용 상수·헬퍼
```

- OpMode는 반드시 `opmodes/` 하위, 종류별(TeleOp/auto/tests)로 분류
- 로직(subsystem/command/localization)과 진입점(OpMode)을 섞지 않는다
- 파일을 옮기면 `package` 선언과 import를 함께 수정하고 빌드로 검증한다

## 우선순위 (시즌 중 시간이 부족할 경우)

1. PIDF 기본 제어 (필수)
2. 오도메트리 (프로파일링의 전제조건)
3. 모션 프로파일링 — 사다리꼴 (가성비 최고, S-curve는 후순위)
4. LQR, 자코비안 등 — 실전 적용보다 세특 이론 탐구용으로 후순위
